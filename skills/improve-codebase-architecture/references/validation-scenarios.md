# Evaluate review behavior

Use clean contexts with equivalent fixture copies for a no-skill baseline and
an explicitly invoked candidate. Supply task inputs and runtime dependencies;
keep grading expectations outside those inputs. Record sources read, proposed
effects, attempted actions when observable, and actual output. Confirm fixture
files remain unchanged. Do not treat a model's action summary as a complete
tool audit when the host does not expose one.

Start with a healthy subsystem, a duplicated-rule regression, and a review-only
adapter/checksum case with useful test coverage and an instruction embedded in
source. Grade whether recommendations follow evidence, retain constraints and
distinct tests, and stay within authority. Measure improvements against the
baseline rather than counting sections or congratulating a longer response.

Exercise these additional branches as controlled scenarios:

- Ordinary explanation, critique, planning, or implementation: do not select
  this explicit-only workflow.
- Missing or shallow history and custom vocabulary/decision paths: use current
  sources and disclose limits without inventing history or creating records.
- Core host without sub-agents: proceed sequentially and disclose the method.
- Missing required companion: stop dependent judgments, continue independent
  mapping, and do not reconstruct or install the missing skill.
- Denied output path, headless host, or offline browser: return a usable
  assessment without bypassing a denial or claiming an unobserved display.
- HTML labels containing markup: encode as text; verify offline rendering and
  narrow-screen readability when a renderer is available.
- Selected or rejected candidate, or a material unresolved design decision:
  compose only the necessary branch, propose records within existing authority,
  and finish without implementation or endless questions.

Record the skill revision or content digest, host and observable capabilities,
requested versus observed runtime settings, results, and evidence limits. Keep
structural checks, simulated capability decisions, real host discovery, and
live execution separate. Supplying a skill path is not discovery evidence.
Unsupported hosts remain unverified. Store sanitized evaluation evidence with
the repository's test fixtures or authorized task/PR records, never runtime
credentials or personal configuration in the skill package.
