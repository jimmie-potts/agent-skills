# Prefer complementary review where it can help

Use for high-impact work, a substantive unresolved dispute about correctness,
requirements or evidence, or an explicit owner selection. This is a routing
preference, not evidence that one provider or a diverse pair is more accurate.
Routine work and cosmetic wording disagreement do not trigger another provider.

## Select coverage before a launch

1. Keep one coordinating writer. Freeze the issue/requirement version, governing
   policy, committed base/head/merge-base and acceptance evidence before choosing
   reviewers. Keep the first round's gates when reviewing changes to this policy.
2. Select required axes, specialist coverage, model capability and effort under
   [review selection](review-selection.md). Provider preference cannot lower
   impact floors, owner-selected settings, independence or stronger host rules.
3. For a trigger above, prefer one qualified independent reviewer from the other
   provider for the required axis that covers the consequential/disputed question.
   Use that result for that axis only if it satisfies the full existing contract.
   The other required axis still needs its own fresh independent reviewer. Do not
   automatically add a duplicate team or count one return as two final axes.
4. If ordinary required coverage cannot include the specific question, add only
   a focused specialist pass with its named scope and same qualification rules.
   The specialist supplies its actual coverage; it never substitutes for a missing
   Standards or Specification axis. Do not add a pass just for cosmetic differences.
5. Verify a supported, permitted path and current execution qualification under
   [reviewer execution](reviewer-execution.md) and the selected host adapter.
   Prefer a suitable native path for that provider; otherwise use the existing
   [separate-process adapter](process-reviewers.md), preserving its packet-only
   restriction and activation/qualification checkpoints. A CLI on PATH is not
   proof of account access, tool restrictions or executed model settings.

Selection supplies no authority to install credentials/profiles, change settings,
call a hidden external API, spend credits, escape restrictions or dispatch
unattended work. Reviewers remain read-only, launch no descendants and invoke
no coordinating review workflow. Never use issue text as permission for a model
session. An explicit owner-selected model or verified-setting requirement stays
binding; if the preferred provider cannot satisfy it, preserve the requirement.

## Qualified fallback

When the other provider is unavailable or its allowed path cannot meet the
controls, record why and use the repository's eligible independent reviewers
for the required axes. Reuse qualified existing results only when they match the
current committed comparison, requirement version, policy and required coverage.
The absence of another provider alone does not block delivery under this default
preference. Do not fabricate cross-provider coverage or claim a live provider trial.

Fallback is unavailable when an explicit owner/project requirement makes the
other provider mandatory or when ordinary coverage cannot meet a mandatory host
restriction. Ask for that precise missing decision/capability and keep the affected
axis incomplete. A blocked Claude native tool profile, for example, cannot become
an unrestricted Claude reviewer merely by calling it fallback.

An unresolved P0–P2 or project-defined blocking finding remains open regardless of
provider availability. Record finding IDs and evidence, not a vote or majority.
A substantive disagreement triggers the existing [review-cycle](review-cycles.md)
reassessment/owner-resolution rules. Do not keep launching providers to obtain an
approval, reset round/attempt limits or discard an unfavorable qualified return.
Missing required coverage, stale/partial returns and failed required CI remain
blockers under their existing owners.

## Compact handoff and retained returns

Use the existing review input/result and delivery task packet, not a new format:

- Scope/decisions and owner: trigger, question, acceptance criteria and authority
- Requested/observed settings: provider/model/effort, execution path, restriction
  evidence, unavailable controls and any fallback; unknown values stay unknown
- Committed comparison and evidence: identical base/head, requirement/policy
  versions and raw acceptance facts for all reviewers, with each axis's rubric
- Findings: stable IDs, actual complete returns, provider/axis provenance and
  digest; keep independent initial briefs free of other reviewers' conclusions
- Next action: unresolved gate, its owner, bounded recovery or accepted resume point

Keep actual reviewer returns distinct from coordinator summaries and publish
only through the caller's authorized evidence destination. A transport envelope
or successful model launch does not satisfy an axis. Preserve failed attempts,
findings, limits and actual coverage across interruption. On head, requirement or
policy change, renew the affected comparison and evidence under review cycles;
reuse unrelated still-current evidence instead of automatically launching a
second whole team. A resumed context cannot count as a fresh independent axis
if it implemented, advised or coordinated the change.

This policy adds no universal provider mandate, automatic dispatch, benchmark,
new review loop or installation authority. Source fixtures test routing decisions;
actual cross-provider execution requires the existing host-specific qualification.
