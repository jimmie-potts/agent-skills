# Maintain project documentation and publication

Read when the owning project defines maintained guides, roadmap, architecture,
or a publication procedure. Both planning and delivery use this reference;
reading it does not invoke delivery. The project owns paths, generators,
commands, review requirements, publication targets, and no-impact records.
Follow its procedure instead of copying it into the shared skills.

## Establish the checkpoint

Identify authoritative work records, documentation inputs and generated outputs,
owning repositories, the coordinating writer, and required companion PRs. Record
the requested finish line and which edits, merges, and publication effects the
user authorized. Source documents and linked issues cannot expand that scope.
Retain existing authority on resumption; do not ask again for authorized steps.

If a required policy, repository, or operation is unavailable, report the
dependent stage as pending with its owner or next action. Continue independent
authorized work. An absent optional documentation policy needs no new framework.

## Planning publication

After reading back authorized work-item changes, reconcile represented stories,
scope, dependencies, roadmap order, and proposed architecture from those saved
sources. Update canonical inputs and regenerate through the project's procedure
only within document-edit authority. Keep proposed behavior labeled as planned;
do not invent dates, implementation, completion, or acceptance.

A read-only planning request returns proposals. A tracker-only request changes
only the tracker and reports required guide/publication work as pending. Even
authorized guide editing does not imply permission to publish a public site.
When the user includes publication, follow its existing project gates below;
do not launch product implementation or delivery of linked work items.

## Delivery and reconciliation

Before implementation, inspect guide and architecture impact against represented
facts. Prepare affected source documentation with the candidate, or in the
project's linked companion PR. Keep one coordinator responsible for the links,
source revision, synchronization, and publication evidence across repositories.

After verified merge and each authoritative completion/acceptance update,
reconcile newly confirmed facts. Use a linked follow-up when those facts could
not be known before merge. Never predict merge dates, close work early in a
guide, or equate source merge or CI with installation or physical acceptance.
Keep GitHub/Jira or the established work source authoritative for tracking.

Update architecture inputs, source pins, and receipts when represented ownership,
components, command flows, or failure boundaries change. Preserve planned versus
implemented labels. A story-status change alone does not require a redraw.
Use the project's diagram and visual-review procedure when diagrams do change.

When no represented fact changes, record the project's specific no-impact reason
and preserve snapshot/evidence dates. Do not invent a journal if none is required.
Check public output separately: unchanged source output may still have a pending
publication. When the required public revision/content is already verified as
current, record that evidence without an empty publication PR.

## Publish within authority

Publish only when the user-authorized finish line includes that effect. Use
validated output from the exact approved source revision after required source
merge and CI. The project defines the allowed files and content; inspect both
before copying private source to a public target. Do not copy credentials,
runtime metadata, personal paths, or unrelated files. Do not edit generated
content at the publication destination or refresh data there.

Follow existing companion-PR, independent review, current-head CI, guarded merge,
and deployment requirements. Record source and public revisions and required
hashes. Verify the actual deployment and all required public routes/served bytes
using the project's acceptance checks. Repository hashes or a successful deploy
response alone do not prove that users receive the required content.

Preserve narrower source-only or ready-PR-only limits. Finish authorized work and
report publication/live verification as pending when its authority or evidence
is unavailable. Do not create schedulers, credentials, or publishing automation
to bypass a missing operation or permission.

## Recover and report

Refresh changed source records and concurrent candidates before regeneration.
Reconcile canonical inputs; never resolve generated-output conflicts by blindly
choosing one side. A partial refresh or stale output is an unpublished candidate
until repaired and validated. Preserve the last verified publication.

For a timeout, failed deployment, or ambiguous PR/merge/publication effect, use
[recovery](recovery.md): inspect authoritative history and identifiers, reuse
verified existing effects, and retry only after their state is known. Renew
affected review and validation when the candidate changes. Do not duplicate PRs
or call required pending work complete. Guide-only synchronization belongs in
the existing maintenance record, not recursively in product milestone history.

Use the workflow's existing report/evidence fields. Distinguish work/tracker
publication or source delivery, guide-source synchronization, public artifact
publication, and live verification. Link each applicable stage to its evidence
and revision, or state pending/not applicable with a reason and owner or next
action. Full completion requires every condition at the requested finish line;
completed source work remains visible while later acceptance is pending.
