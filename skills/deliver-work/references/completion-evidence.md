# Match completion claims to current evidence

Read before a completion claim, acceptance walkthrough or handoff. Use the
existing task evidence and Execution record; add no second closeout format.
Do not invoke close-work or write memory merely to finish delivery.

## Evidence-to-claim check

For each stage claimed, inspect the source that actually establishes it and
retain four facts in existing Evidence: source/link, observed revision and
target, observation time, and verification limit. Use structured provider
results and project verification tools. Never treat a success-like phrase in
arbitrary prose, a task checkbox or an earlier assistant claim as proof.

Immediately before posting, refresh volatile facts using authorized reads:
PR/target inclusion, required checks, installed target/content and acceptance
state where relevant. Immutable evidence may be reused for the same revision;
its current applicability must still be checked. A later installed revision
may include the source change, but inclusion must be demonstrated with the
owning procedure rather than inferred from a larger version number.

If a fresh read is unavailable or outside authority, keep the earlier result
explicitly historical and mark current status unknown. State when and where
it was observed and what the owner can verify next. Do not open private runtime
stores, contact devices or repair host settings to obtain a nicer closeout.

| Claim | Evidence that can support it | Evidence that cannot substitute |
| --- | --- | --- |
| Source merged | Current merged PR/readback, immutable merge revision, actual target inclusion and required post-merge checks | An accepted merge request, queue entry or old branch name |
| Installed | Owning procedure's current target/link/content readback at an identified revision | Source merge, old installation receipt or file transport acknowledgment |
| Active in client | Required current client discovery/activation readback for that installed target | Link existence, source tests or a simulator frame |
| Visible/physical acceptance | Required observation on the declared candidate and actual surface/device, including owner acceptance when required | Transport acknowledgment, a different candidate or simulator-only result |

Name missing stages separately. Preserve the project's current required gates,
explicit accepted limitations and source-only opt-out procedure. Historical
acceptance of one limitation is not permission to waive it on another delivery.
Optional memory capture does not invalidate accepted delivery. Only attempt it
when explicitly authorized through a supported destination, report failure
separately, and preserve required evidence in its authorized durable location.
A required missing install or acceptance result remains pending regardless of
whether memory succeeded.

## Write the owner's next step

Open with finished, remaining and owner action (or none), in one or two plain
sentences. Link technical evidence below; keep existing Execution record rows
and parseable Closeout record keys unchanged. Report source and installed/active
results separately even when they share one revision. Do not change an issue's
state automatically just because a readable reply has been written.

When acceptance remains, reuse the owning preview procedure and capability
preflight. Recover approved setup facts from available authorized context before
asking the owner to repeat them. Finding a target never grants control of it.
Give the current candidate, starting condition and numbered actions, with the
expected visible result after every action. For an authorized recording, mark
the pointer/control clearly and show the result after each action. State the
exact resume point and which evidence will complete the remaining gate. If the
current surface cannot provide the required recording/observation, name the gap;
never substitute a still image or transport receipt for required interaction.

## Representative handoff

Synthetic example; no live installation or device acceptance is claimed:

Source revision `aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa` is merged and its
required checks passed. Installation is still pending. Owner action: approve
the already prepared catalog update, then perform the current client check.

Candidate: `aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa`, catalog on the approved
host. Starting condition: the owner-approved update has finished with clean
content/link readbacks; use the agreed neutral client session, without a local
same-named skill masking discovery.

1. Open the client's supported skill listing. Expected: the changed skill is
   listed once from the approved catalog location.
2. Inspect its resolved source using the client's supported readback.
   Expected: the location and installed content match the candidate revision.

Resume at the installation/client-evidence checkpoint with the observed path,
revision and result. Do not close the issue until the owning completion rules
pass or the owner explicitly accepts a recorded limitation. This walkthrough
neither authorizes the update nor establishes that the checks have happened.
