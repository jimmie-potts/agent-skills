# Plan GitHub work

Resolve the owner/repository and issue identity from current authorized sources.
Bare numbers need an unambiguous namespace. Confirm an existing reference is an
issue, not a PR. Read repository instructions and existing issue conventions;
search and paginate relevant open/closed issues and linked implementation before
proposing new work. Closed does not prove delivered: inspect disposition and
acceptance evidence when reuse or dependencies depend on it.

Use issue bodies and existing fields for outcome, criteria, verification, and
assessment. Labels and Projects fields are separate from issue open/closed state.
Reuse them only when their established meanings and requested changes match.
Do not create labels, Projects, fields, or board membership merely for this skill.
Keep unresolved requirements and active implementation evidence when refining
existing descriptions; re-read before overwriting any authorized field.

For authorized publication, create prerequisite items before items needing
their references. Use full issue URLs for dependencies. Where supported, add
native blocked-by relationships using verified issue identities, then read
the relationships back and check direction and cycles. Do not confuse issue
numbers with internal IDs or dependencies with parent/sub-issue grouping.
If native linking is unavailable, retain explicit body links and disclose the
limitation; if project policy requires native links, leave that gate pending.

Read back issue identity, body/fields, state, and relationships. Preserve
unrelated labels, assignees, milestone, Projects values, and current work. An
authorized planning update does not close/reopen issues, transition delivery,
or publish PRs unless separately included in the request. If publication times
out, reconcile authoritative reads/history before retrying; do not create a
second issue just because search has not indexed the first.
